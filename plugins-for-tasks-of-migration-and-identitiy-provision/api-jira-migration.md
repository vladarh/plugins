Миграция через REST API в изолированном контуре (Air-Gapped Environment) — это самый отказоустойчивый инженерный подход. Поскольку скрипту миграции не нужен доступ в интернет, а взаимодействие между старым и новым сервером происходит исключительно внутри вашей закрытой локальной сети (LAN), этот метод полностью решает проблему лицензирования плагинов и прыжка версий (Jira 8 → 10, Confluence 7 → 9).
Ниже приведена подробная архитектура и пошаговый алгоритм, как развернуть и выполнить такую миграцию.
------------------------------
## Архитектура процесса в закрытом контуре
Вам понадобится промежуточная "Машина миграции" (инженерный хост / виртуальная машина), развернутая в той же изолированной сети, что и серверы Atlassian.

[ Исходный контур ]          [ Машина миграции ]          [ Целевой контур ]
  Jira 8 / Conf 7              (Python + Скрипты)           Jira 10 / Conf 9

        |                              |                           |
        | ----- REST API (JSON) -----> |                           |  (Синхронизация юзеров)
        |                              | <==================== [ Keycloak ]
        |                              |                           |
        |                              | ----- REST API (JSON) ---->

На этой машине настраивается рабочее окружение:

   1. Интерпретатор: Python 3.10+.
   2. Зависимости (Библиотеки): Пакеты переносятся в контур в виде готовых wheel-файлов (.whl) и устанавливаются офлайн:
   
   pip install requests requests_toolbelt atlassian-python-api --no-index --find-links=/path/to/whl/
   
   
------------------------------
## ЭТАП 1: Подготовка (Критически важно для Полноты данных)
Перед запуском скриптов необходимо выполнить синхронизацию учетных записей.

* Синхронизация через Keycloak: Запустите SCIM-синхронизацию пользователей на целевых Jira 10 и Confluence 9.
* Зачем это нужно: Если скрипт попытается создать задачу от имени ивана_иванова, а Keycloak еще не создал этого пользователя в базе Jira 10, API выдаст ошибку 400 Bad Request или запишет автором администратора, что обнулит полноту данных (Completeness).

------------------------------
## ЭТАП 2: Пошаговый алгоритм миграции Jira (8 → 10) через REST API
В Jira 8 и Jira 10 базовая структура данных задач (Issues, Comments, Attachments) на уровне JSON полностью идентична. Скрипт работает по принципу ETL (Extract, Transform, Load):
## Шаг 1: Извлечение (Extract)
Скрипт делает постраничный запрос (Pagination) к старой Jira 8 по JQL нужного проекта:

* Запрос: GET /rest/api/2/search?jql=project=PROJ&expand=renderedFields,names
* Скрипт сохраняет полученные JSON-массивы задач во временные файлы на машине миграции.
* Скачивание вложений: Для каждой задачи скрипт смотрит на поле attachment, берет прямую ссылку (например, /secure/attachment/10100/file.png) и физически скачивает файлы в локальную папку.

## Шаг 2: Трансформация (Transform)
Скрипт на лету адаптирует JSON под новую систему:

* Удаляются системные ID старой Jira (которые изменятся на новом сервере).
* Маппятся кастомные поля (если ID поля Story Points в старой Jira был customfield_10001, а в новой стал customfield_10500, скрипт переименовывает ключ в JSON).

## Шаг 3: Загрузка (Load)
Скрипт авторизуется в Jira 10 под токеном администратора (Personal Access Token) и последовательно выполняет:

   1. Создание задачи: POST /rest/api/2/issue (передается очищенный JSON).
   2. Прикрепление вложений: POST /rest/api/2/issue/{issueKey}/attachments (используется multipart/form-data для загрузки скачанных ранее файлов).
   3. Добавление комментариев: Скрипт итеративно отправляет старые комментарии через POST /rest/api/2/issue/{issueKey}/comment.

⚠️ Важный нюанс импорта авторов (User Simulation):
По умолчанию REST API создает задачи от имени того, чей токен используется (администратора). Чтобы автором стал реальный пользователь, в Jira 10 администратору должно быть временно выдано право "Modify Reporter" и "Create Comments on Behalf" в схеме прав (Permission Scheme) мигрируемого проекта. Тогда в теле POST-запроса можно будет явно указать: "reporter": {"name": "ivan_ivanov"}.

## ЭТАП 3: Пошаговый алгоритм миграции Confluence (7 → 9) через REST API
Поскольку Confluence 9 перешла на новую версию REST API (v2), для миграции страниц используется стабильное ядро API v1, которое сохранено для обратной совместимости.
## Шаг 1: Сбор иерархии страниц (Extract)

   1. Скрипт запрашивает список всех страниц пространства: GET /rest/api/content?spaceKey=SPACE&expand=body.storage,ancestors.
   2. Скачиваются бинарные файлы вложений для каждой страницы: GET /rest/api/content/{id}/child/attachment.

## Шаг 2: Создание структуры на целевом сервере (Load)
Чтобы не нарушить иерархию (дерево страниц), скрипт выполняет рекурсивное создание:

   1. Сначала создается главная (домашняя) страница пространства в Confluence 9 через POST /rest/api/content. В теле запроса передается оригинальный XHTML-код (body.storage.value), который Confluence 7 и 9 понимают одинаково.
   2. Скрипт получает новый ID созданной страницы в Confluence 9.
   3. Затем скрипт создает дочерние страницы, явно указывая новый ID родителя в массиве "ancestors": [{"id": "NEW_PARENT_ID"}].
   4. Загружаются вложения: POST /rest/api/content/{new_id}/child/attachment.

## Пример структуры простого Python-скрипта для миграции задачи
Инженеры пишут подобные скрипты индивидуально под миграцию, базовый логический блок выглядит так:

import requests
source_url = "http://jira8-isolated.local"target_url = "http://jira10-isolated.local"headers = {"Authorization": "Bearer YOUR_TOKEN", "Content-Type": "application/json"}
# 1. Выкачиваем задачу из Jira 8source_issue = requests.get(f"{source_url}/issue/PROJ-1", headers=headers).json()
# 2. Формируем чистый пакет для Jira 10payload = {
    "fields": {
        "project": {"key": "PROJ"},
        "summary": source_issue["fields"]["summary"],
        "description": source_issue["fields"]["description"],
        "issuetype": {"name": source_issue["fields"]["issuetype"]["name"]},
        "reporter": {"name": source_issue["fields"]["reporter"]["name"]}, # Требует прав Modify Reporter
        "priority": {"name": source_issue["fields"]["priority"]["name"]}
    }
}
# 3. Создаем в Jira 10response = requests.post(f"{target_url}/issue", json=payload, headers=headers)
print(f"Создана задача: {response.json()['key']}")

## Анализ полноты данных (Completeness) при REST API методе

| Сущность | Процент переноса | Комментарий |
|---|---|---|
| Текст, темы, описания | 100% | Базовые строки переносятся без изменений. |
| Вложения и файлы | 100% | Переносятся физически как файлы, связи восстанавливаются скриптом. |
| Комментарии | 100% | Добавляются итеративно к каждой созданной задаче/странице. |
| Авторы (Reporters) | 99% | При условии, что пользователи уже синхронизированы через Keycloak, а у админа есть право "Modify Reporter". |
| История изменений (History) | 0% | Главный минус REST API: Вы не можете через стандартный API записать логи системных изменений (например, "01.02.2023 Петр перевел задачу в статус In Progress"). Новые задачи в Jira 10 начнут историю "с чистого листа". Ворклог (Worklogs) при этом перенести можно отдельными POST-запросами. |

## Резюме
REST API миграция в изолированном контуре — это самый надежный способ сохранить контент и файлы, если вам не важна детальная история переходов задач по статусам за прошлые годы. Метод полностью избавляет от необходимости использовать патчи, агенты или покупать CMJ от Appfire.
